## 1. Source Payload Preservation

The pinned Unix scanner can send the same file chunks to hashing and an encrypted payload capture without reopening the source pathname. The scanner retains its inode, length, timestamp, mount, and endpoint checks. A changed source aborts the scan, drops the capture, and withholds encrypted stream finalization. Manifest-only sinks retain their existing behavior through default content callbacks.

`PayloadCapture` wraps a metadata sink and an encrypted streaming writer. It supports regular files and directories with Unix byte paths and no requested metadata. Each file header declares source, path encoding, components, and canonical decimal length. Exactly that many raw bytes follow, then a canonical manifest entry containing the content digest. Directories carry their manifest entry directly. A terminal summary declares canonical decimal entry count, file count, and payload length. The enclosing encrypted stream authenticates its terminal record and rejects ciphertext suffixes.

The internal version-one domain is `relic/source-payload/v1` followed by a zero byte. Its encryption context hashes that domain and the canonical complete capture binding. Plaintext starts with the same domain. Records contain a one-byte tag, four-byte big-endian canonical JSON length, and JSON bytes. Tags are zero for the terminal summary, one for a directory, two for a file header, and three for a file trailer. File contents are length-delimited raw bytes between header and trailer, without a second whole-file buffer. Unknown tags, noncanonical JSON, duplicate JSON members, invalid paths, mismatched file identities or checksums, invalid counts, and trailing plaintext fail validation.

## 2. Bounded Verification

Limits cover entries, depth, individual and aggregate file bytes, plaintext bytes, and ciphertext bytes. Metadata frames are at most 256 KiB, depth is at most 128 components, and data callbacks receive at most 64 KiB. The scanner and payload reader zeroize their reusable file buffers; the encrypted spool reuses its record buffer. Metadata parsing allocates only within the frame bound. Source size declarations are checked before a consumer receives that file. Aggregate resource admission and storage reservations remain caller responsibilities.

`visit_payload` validates each file's bytes against its trailer, all summary counts, and complete encrypted authentication. Its callbacks receive provisional plaintext. Consumers must withhold publication until the entire visit succeeds and must discard staged output on error. Per-record authentication does not establish completeness. This API does not grant filesystem authority or publish restored files.

`verify_payload` sends the recovered entries to a fresh bounded encrypted sorter and compares the resulting strict logical manifest and entry count with the expected capture manifest. This also rejects duplicate paths and binds source identities and paths, lengths, content digests, and supported metadata. Its sorter is disposable after any failed verification. A valid payload with a different logical manifest cannot substitute for the expected capture.

## 3. Evidence and Remaining Integration

The real filesystem fixture reserves node/job resources, binds capture state before source reads, scans through a pinned endpoint, writes encrypted payload to disk, synchronizes it, derives the manifest from the encrypted ordering sink, and deletes the source tree. It then authenticates the payload against that manifest and recovers files through the safe restore primitives. Test-only recovery buffers have a fixed small fixture size. Production recovery still needs a bounded staged tree and coordinated publication.

The adversarial fixtures exercise empty files, encryption record boundaries, multi-record files, changed source contents, wrong capture bindings and keys, authenticated semantic corruption, unsafe paths, oversized lengths, quotas, cancellation, failing consumers, incomplete final authentication, duplicate entries, and mismatched expected manifests. Native artifact milestone `8073389` passed all selected targets in [run 42813731012](https://github.com/mayazrakib/relic/actions/runs/42813731012); subsequent payload changes need their own native run.

This is an internal source-capture stream, not a destination archive format or a complete backup command. Durable payload ownership, opaque key-reference linkage, crash reconciliation, cleanup, immutable provider views, full metadata, Windows scanning, production restore staging, and archive adapter integration remain unfinished. A manifest artifact journal alone does not supply durable ownership for this separate payload file. Neither successful local tests nor native component tests establish full-system conformance.
